## Proposed implementation sequence after approval

1. **Add only required state.** Prepare additive, nullable, indexed `archived_at` columns on `school_years` and `sections`; cast as datetime in the matching models. Existing rows start unarchived. Do not add term/exam state, soft-delete traits, global archive scopes, cascade deletes, a staff-account anonymization timer, or a section-assignment history table. The timestamp design remains a technical proposal until approved under Gate B0.
2. **School-year transitions.** Propose `POST /api/settings/school-years/{schoolYear}/archive` and `/restore` behind `settings.system.manage`. Lock the year/current-year rows in one transaction; reject archiving current/already archived and restoring non-archived records; preserve the same ID and `is_current=false` on restore. Record distinct `school_year.archived`/`.restored` audit events in that transaction. Reject `makeCurrent` for an archived target. On archived-year PATCH, allow audited label correction only; reject dates. Existing label uniqueness and date overlap checks include archived years. Existing account-based date lock remains after restore.
3. **Parent term/exam guard.** Keep term and exam rows untouched and readable under the archived parent. Reject term/exam create/update through direct API calls while the parent is archived; restore the parent to resume eligible edits. Retain term sequence uniqueness, year/term date locks, and existing FK constraints. No independent term Archive/Restore route.
4. **Section transitions and assignment guard.** Propose `POST /api/settings/sections/{section}/archive` and `/restore` behind `settings.system.manage`; record distinct atomic audit events. Preserve `active` unchanged so restore returns the prior value; existing inactive rows remain inactive, not Archived. Permit audited, unique name correction while archived but reject changing `active` until restored. Keep names reserved across states. Student options exclude both inactive and archived sections; direct student POST/PATCH rejects a new/changed inactive or archived section ID while permitting an unrelated edit that retains the student's existing section ID. Never null or move existing student links.
5. **Read contracts.** Extend `GET /api/settings/school-years` with an explicit ordinary/Archived selector and archive state field, retaining existing year/term/exam response fields. Extend grade/section read output with separate `active` and archive state, and a selected view filter without changing fixed grade order. Preserve Accounting's settings read-only access. Propose scope names/response fields in the API contract before coding callers; do not expose admin-only settings data to financial roles that lack `settings.system.view`.
6. **Financial view scope, not financial mutation.** Extend only the existing account/report list APIs as needed with a clear ordinary versus Archived scope. Ordinary `DailyReportController` payment rows, method/cashier totals and related void rows exclude archived-year payments; Archived scope returns those records with the existing valid/void-pending/voided rules intact. `OutstandingReportController` and billing-account list apply the same year-state choice to their rows and pagination/meta. Direct authorized account detail remains intact. The default ordinary scope must be labeled in responses so clients, CSV and print can disclose it. Do not alter persisted close-out totals, payment history, dashboards, opening-balance conversion, student statement's current-year contract, or any unrelated endpoint without a separately approved requirement.
7. **Audit and compatibility review.** Ensure every transition/correction is audited with actor, timestamp, entity ID and before/after state; audit failure rolls back the state change. Verify older clients can read additive fields and that archived-year `all` account filters are clearly defined. Keep capability map unchanged. Update `02-Architecture/Backend-API-Contract.md`, schema dictionary/ERD and setup notes only after the implementation contract is finalized.

The exact route names, query parameter names and archive timestamp schema above are **PROPOSED technical choices**, not already approved code. Prefer the smallest contract compatible with existing clients and the approved scope behavior.
