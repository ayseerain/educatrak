# Backend B10 — Close-out and Cashier/Accounting Reconciliation

- **Timestamp:** Thursday, November 12, 2026 — 17:54:23 +08:00
- **State:** Owner review; target-database verification blocked.
- **Scope audited:** Cashier close-out totals, variance/reason validation, daily locking, read scopes, Accounting sign-off, test-only business-date simulation, and concurrency safeguards.

## Verified evidence

- Cashier-only submission uses the current business date; the same Cashier cannot submit twice for that date. A non-zero cash variance requires a reason.
- Close-outs have no edit endpoint. Cashiers see only their own history; Accounting sees all history and is the only role able to sign off once. A second sign-off returns an unprocessable response.
- The business-date simulator is session-scoped, requires the Cashier capability, and returns 404 outside local/testing even when enabled.
- Focused `CashierOperationsTest` and `CapabilityMapTest` passed: 77 tests / 494 assertions. Tests use isolated SQLite data only.

## Open findings

1. M13 requires system totals by payment method, but the live close-out API currently calculates/returns only cash. Cash variance must remain cash-only, while method totals require an approved response/UI contract.
2. The code locks close-out rows and the schema has a unique Cashier/date constraint, but concurrent double-submit and sign-off behavior has not been proven on target MySQL.
3. The existing B09 atomic-audit transaction issue applies to close-out submission and remains open; this audit does not duplicate it.
