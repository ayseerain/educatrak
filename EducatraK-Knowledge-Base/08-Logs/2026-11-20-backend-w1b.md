## What changed
- Migration `2026_11_20_010000_add_versioning_to_payment_plans.php`:
  - adds `payment_plans.version` (default 1) and `previous_version_id` (self FK, RESTRICT);
  - replaces `unique(name)` with `unique(name, version)`;
  - changes `billing_accounts.payment_plan_id` from SET NULL to RESTRICT;
  - `down()` refuses while revised versions exist.
- `ComputeInstallmentScheduleAction` (integer centavos):
  - the down payment is due on the anchor date: an amount in centavos, or basis points rounded down;
  - installments take floor(remaining × bp / 10000), with the remainder on the last;
  - due date = anchor + `due_day_offset`;
  - zero rows are omitted, and the schedule sum always equals the total.
- `FinanceSettingsController`: create, revise (new version N+1; old version deactivated and kept), deactivate, and preview. The plan list now includes `version` and `previousVersionId`.
- 4 routes. Writes need `settings.finance.manage`; preview needs `settings.finance.view`. No delete route.

## Database impact
One approved additive migration. It was exercised only on isolated SQLite `:memory:`; no shared or production database was touched.

The first run of the upgrade test exposed a SQLite-only data-loss path. Rebuilding `payment_plans` fired the old ON DELETE SET NULL on `billing_accounts.payment_plan_id`. The migration now avoids rebuilding `payment_plans` on SQLite and defers FK checks for the `billing_accounts` rebuild. That table's children are all RESTRICT, and the test proves an empty `foreign_key_check`. MySQL alters these keys natively, but this is unverified on the target.
